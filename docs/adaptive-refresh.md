# Adaptive refresh and host politeness

Background ticks query an index on `(autoMuted, archivedAt, nextSyncAt)` for due subscriptions. New feeds have a nullable schedule (immediately eligible); the additive SQLite/Postgres migration scatters existing subscriptions over the next 15 minutes. No Article bookkeeping writes are involved. `nextSyncAt` is persisted because querying and calculating every feed on every tick would keep waking the database. Deployment jitter changes only the new column.

After a successful fetch, including a cheap conditional GET/304, the last 40 stored publication timestamps determine the median interval. Duplicate timestamps and clusters less than five minutes apart do not inflate publication frequency. Missing publication times fall back to creation time. Future/invalid times are ignored. Half the time since the most recent publication provides an idle floor, preventing old backfill dumps from triggering rapid polling. New/single-item feeds start at 60 minutes. Estimated cadence is stored separately for display.

Automatic intervals are clamped to 15 minutes–24 hours. `FEED_MIN_REFRESH_MINUTES` and `FEED_MAX_REFRESH_MINUTES` configure these bounds. Existing category/user interval preferences remain a minimum; explicit per-feed minutes take precedence over cadence and inherited preferences, subject to the server minimum. Explicit/inherited values above the automatic ceiling remain respected. Empty feed interval means Automatic. Feed management's edit dialog displays the estimated publications/day and next fetch time. Interval edits invalidate that feed's schedule. Changes to category/global preferences take effect on the next scheduled fetch (at most the current interval).

Reader boot uses due selection and the shared host gate. Manual single-feed refresh and user Refresh all bypass due times; archived and auto-muted feeds remain excluded from bulk refresh. There is currently no WebSub subscription state in FeedFerret, so there is no reliable push-capability signal to apply a maximum interval to.

The shared in-process background host gate permits one feed fetch per hostname and spaces request starts by 2 seconds (`FEED_HOST_SPACING_MS`). Different hosts can run concurrently, across users. Host backoff is checked again after waiting. 429, 503 and 403 defer work without increasing feed failures, triggering error notifications, or auto-muting. Retry-After delta seconds and HTTP dates are honoured (existing seven-day sanity cap), with exponential local backoff otherwise. Blocked hosts start at 15 minutes. Deferred nextSyncAt survives restart; host gate/backoff state does not. Manual fetches bypass the spacing gate but rate-limit responses still defer without feed failures. All network access remains in the existing safeFetch fetchers.

The gate applies to feed fetch operations (including their parser), not to all article/full-text HTTP requests or redirect destination hosts. Multiple app replicas have independent gates; global distributed politeness would require a shared lease store.

Rollback: revert the application change; leave the additive columns/index in place. No destructive down-migration is required.
